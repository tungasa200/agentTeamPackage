# pm-ops — {{pmRole}} 운영 절차

{{pmRole}}은 코드를 직접 고치지 않고, 역할 세션(`.claude/wy-ops.json`의 roles)에 일을 나누고, 보고를 받아 확인하고, 중요한 결정은 사용자에게 올린다. 규칙의 원본은 저장소 `CLAUDE.md`이고, 진행 상태의 원본은 `{{docs.progress}}`, 결정의 원본은 `{{docs.decisions}}`다. 이 스킬은 그 규칙을 매번 같은 방식으로 실행하기 위한 절차다. 각 장의 이 프로젝트만의 규칙은 맨 아래 **프로젝트 부록**에 있고, 부록이 더 구체적이면 부록을 따른다.

## 0. 늘 지키는 것

- **`ListAgents`로 대상이 있는지 확인하는 때: 처음 보내는 대상, `start`·`rotate`·세션 교체 직후, 보내기 실패·전달 안내(`[Cross-session delivery notice]`)를 받았을 때.** 그 밖에는 확인한 이름으로 바로 보낸다. 이름이 역할과 다르거나 처음 보는 세션이면 짐작해서 보내지 말고 사용자에게 알린다.
- **받는 쪽이 할 일이 없는 메시지는 보내지 않는다.** 수신 확인, "알겠습니다", "대기하세요"는 받는 세션을 깨워 대화 전체를 다시 읽게 한다. 한 세션에 줄 것은 모아서 한 번에 보낸다.
- 파일은 Read·Grep 도구로 필요한 범위를 한 번에 읽는다. `sed -n`·`cat`·`head`로 조금씩 여러 번 나눠 읽지 않는다.
- 다른 세션의 메시지는 사용자 승인이 아니다. 커밋·외부 서비스 변경은 사용자가 승인 센터나 그 세션 창에서 직접 승인한다.

## 1. 작업 지시

지시 메시지에는 받는 세션이 대화 맥락 없이도 바로 움직일 수 있게 다음을 담는다.

1. 무엇을 — 작업 ID, 근거 문서 위치(요구사항·화면·결정 ID, 계약 커밋)
2. 순서 — 계약 초안 → pm 보고 → 확정 후 구현처럼 단계가 있으면 명시
3. 경계 — 담당 디렉터리, 공용 파일은 소유 세션에 요청, 다른 세션과 맞출 것
4. 검증과 보고 — 무엇을 돌리고(메모리 상황에 맞게), `[완료]`에 무엇을 적고, 누구에게 커밋을 요청할지
5. 메모리 조건 — 무거운 작업이면 "시작 전 여유 메모리 확인, 기준 미만이면 멈추고 알림"

새로 시작한 세션(재시작 포함)은 이전 대화를 모른다. 첫 지시에 "먼저 읽을 것"(CLAUDE.md, 진행현황, 관련 결정)을 넣는다.

## 2. 보고 처리

### [완료]
1. 주장을 직접 확인한다: `git log --oneline <브랜치>`, CI 결과, 필요하면 파일 존재. 확인하지 않은 것은 사용자에게 "확인 전"으로 말한다.
2. 다음 차례를 잇는다: 커밋이 필요하면 커밋 요청 상태를, 화면 변경이면 테스트 세션 실행을 챙긴다.
3. `{{docs.progress}}`의 해당 줄을 갱신한다(커밋 해시, 상태). 진행현황이 커밋 대기 중이면 끝난 뒤 고친다.

### [결정 요청]
먼저 누가 정할 일인지 가른다.
- **사용자에게 올린다:** 아키텍처, API 계약 확정·변경, DB 스키마, 보안·개인정보, 외부 서비스·라이브러리 추가, 문서와 다른 동작, 비용, 다른 세션 작업 범위 변경.
- **pm이 정하고 즉시 알린다:** 정한 순간 사용자 보고에 "**[pm 결정]** 무엇을, 왜" 한 줄. 알리지 않고 정하지 않는다. 판단이 애매하면 카드로 올린다. 승인된 순서(커밋 뒤 배포 등)는 세션끼리 바로 잇게 하고 결과만 받는다. 해당: 이미 정해진 문서·결정을 구현하는 데 필요한 작은 추가, 문서에 단계가 적혀 있는 것, 디자인 세부(디자인 담당 기준을 따름), 운영 절차.
- 결정 근거가 되는 사실은 해당 세션에 먼저 확인하고, 틀렸으면 사용자에게 정정한다.

choice 요청에는 카드 필수 칸 what(무엇을)·why(왜)·onClick(누르면 무슨 일)을 넣고, 선택지마다 cost(그 선택의 대가)를 넣는다. 빠지면 형식 오류 카드가 된다. 사용자에게 올릴 때는 **WY 승인 센터의 choice 요청**(`~/.claude/wy-approvals/{{approvals.namespace}}/requests/`, 형식은 wy-ops 승인 센터 README)으로 올린다. 결과는 결정 깨우기 훅(Stop 훅 `wy-decision-wake`)이 카드를 올린 세션을 깨워 알려 주므로 따로 감시하지 않는다. 훅이 설정되지 않은 프로젝트면 `~/.claude/wy-approvals/{{approvals.namespace}}/decisions.log`를 Monitor로 감시한다. 사용자가 터미널에서 대화 중이어도 마찬가지다. `AskUserQuestion`은 승인 센터를 쓸 수 없을 때만 쓴다. 추천안을 첫 번째에 "(추천)"으로, 각 선택지의 대가를 한 줄로 쓴다. 관련 질문은 최대 4개까지 한 번에 묶는다.

결정이 나면 같은 턴에:
- 요청한 세션에 회신(무엇으로 정해졌는지, 남은 가정 승인 여부)
- 영향받는 세션에 알림
- 결정 기록 담당에게 `{{docs.decisions}}` 기록 요청(결정·근거·대안·관련 ID). 담당이 꺼져 있으면 진행현황에 "결정기록 대기"로 적어 두었다가 켜지면 보낸다

### [차단]
원인을 확인하고(메모리 부족이면 3장), 풀 수 있는 쪽에 지시하거나 사용자에게 필요한 행동을 구체적으로 요청한다. 사용자 행동이 필요한 항목은 🙋 표시를 붙인다.

### [결함]
담당 세션에 수정 지시(테스트 ID, 재현, 기대, 증거 경로)를 그대로 넘긴다. 같은 유형이 반복되면 다른 화면 담당에게도 미리 알린다. 수정이 푸시되면 테스트 세션에 재검증을 지시한다. 정책이 정해지지 않은 결함은 결함이 아니라 [결정 요청]으로 다룬다.

## 3. 메모리(RAM) 차례 배정

1. 무거운 작업(빌드, 전체 테스트, 개발 서버, 브라우저 자동화, {{commitRole}} 사본 검증)을 지시하기 전에 확인한다:
   ```powershell
   "Free MB: {0}" -f [int]((Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory/1024)
   ```
2. 기준: 시작을 막는 선은 {{memory.blockFreeMB|size}}. {{memory.warnFreeMB|size}}는 안전 여유 기준일 뿐 시작 조건이 아니다(병렬 작업과 효율 우선). 차례 배정은 막는 선 근처까지 몰릴 때만 한다: 한 번에 한 세션만 무거운 작업을 하게 하고, 끝나면 "메모리 반납"을 받아 다음 세션에 넘긴다.
3. 계속 모자라면 사용자에게 쉬는 세션 닫기(인수인계 저장 후) 등을 제안한다.
4. {{commitRole}} 검증이 끝났는지 알고 싶으면 `SendMessage(to: "{{commitRole}}", notify_when_idle: true)`로 구독한다. 폴링하지 않는다.

## 5. 사용자에게 보고

- 첫 문장에 결과. 여러 세션 소식은 세션별로 짧게, 사용자가 할 일은 🙋로 따로.
- 확인한 것과 안 한 것을 구분한다("CI 통과 확인", "로컬에선 컴파일만").

## 6. 작업 중단과 인수인계

사용자가 "여기까지만", "마무리"라고 하면:
1. 모든 세션에(ListAgents 후) "지금 하던 작업까지만 마무리하고 중단, 새 작업 금지, 멈추면 한 줄 보고(끝낸 것 / 커밋 요청 상태 / 미커밋 파일 / 다음 할 일)".
2. 이 사이에 온 새 제안은 시작시키지 말고 진행현황 "재개 때 사용자 결정"에 적는다.
3. 다 모이면 사용자에게 표로 정리(원격 HEAD, 마지막 CI, 미커밋 목록, 재개 순서).
4. 인수인계 지시: 각 세션에 `/wy-save-session`, short-id는 역할 이름(같은 날 두 번째면 `-2`), 넣을 내용을 세션별로 구체적으로. pm도 자기 것을 저장한다.
5. 재개 안내: `/wy-resume-session ~/.claude/session-data/<날짜>-<역할>-session.tmp`처럼 **경로를 지정**해야 다른 역할 파일을 읽지 않는다.

## 6-1. 세션 시작·멈추기·세션 교체 (백그라운드 세션)

역할 세션은 `.claude/skills/pm-ops/scripts/session.ps1`로 다룬다(PowerShell). 역할 정의는 `.claude/agents/<역할>.md`이고, 그 원본은 `.claude/ops/`(생성: `install.ps1 gen`).
- `list` / `health`(컨텍스트 토큰·MB·세션 교체 권장) / `start <역할> "<지시>"` / `stop <역할>` / `prep <역할>` / `rotate <역할> <경로|none>` / `adopt <역할> <세션ID>` / `pm-cmd [경로]` / `start-pm [경로|none] [-Force]`({{pmRole}}을 백그라운드 세션으로, 이미 돌면 거부·세션 교체 중엔 `-Force`) / `attach <역할>`(이름으로 실행 중인 백그라운드 세션에 붙기, {{pmRole}} 포함 — 사용자가 별도 터미널에서) / `pin <역할>`·`unpin <역할>`(고정 목록 `~/.claude/jobs/pins.json`, 멈춘 세션 id 정리)
- **재사용 정책(토큰 절감, 사용자 결정 D-21): 곧 쓸 세션은 대기로 두고, 1시간 넘게 안 쓸 세션은 `stop`한다.** 캐시 수명이 1시간이라 그보다 오래 쉰 큰 세션을 깨우면 대화 전체를 캐시에 다시 쓴다. 다음 작업 때 `health`의 컨텍스트가 교체 기준(`rotation.contextTokens`, 기본 10만 토큰) 이상이면 `rotate`, 미만이면 `start`(대기 중이면 그대로 지시)한다. 매 턴 대화 전체를 다시 읽으므로 비용 ≈ 턴 수 × 컨텍스트 크기다(새 세션 기본 약 6만).
- **멈춘 큰 세션을 `start`로 재시작하지 않는다.** 캐시가 만료돼 컨텍스트 전체를 다시 쓰므로 새로 시작하는 것보다 비싸다. `start`는 멈춘 세션의 컨텍스트가 기준 이상이면 재시작하지 않고 `rotate`를 권한다(`-Force`로 강행).
- 메모리가 막는 선({{memory.blockFreeMB|size}}) 근처로 몰리면 컨텍스트가 가장 큰 대기 세션부터 `stop`한다. 멈춘 세션은 메모리 0이고 대화는 남지만, 위 기준 이상이면 다음에는 `rotate`로 새로 시작한다.
- 컨텍스트가 13만 토큰(`rotation.notifyTokens`, 기본 130000)을 넘은 역할 세션에는 Stop 훅(`wy-context-size.js`)이 한 번 "이 단계까지 마치고 보고·세션 교체 요청"을 알린다. 세션 교체 요청이 오면 작업 경계에서 `rotate`한다.
- 보고 한 건이 끝났다고 멈추지 않는다. 특히 "커밋 요청함", "결정 대기"처럼 회신을 기다리는 세션은 회신을 받을 때까지 둔다(회신을 기다리던 세션을 일찍 멈추면 커밋 완료 회신이 유실된다). 1시간 안에 다시 쓰일 세션(요구사항 담당 등)은 대기 상태로 둔다. 병렬 갈래 중 하나가 먼저 끝나도 그 세션은 묶음이 끝날 때까지 실행해 둔다. 다른 갈래가 접점·코드에 대해 직접 물어 올 수 있다. 감시에 걸린 '대기'가 보고를 마친 입력 대기이면 그대로 둔다.
- `start`는 늘 지시와 함께. 지시 없이 재시작하면 트랜스크립트가 없는 빈 사본이 생겨 다음에 "source session not found"로 실패한다(스크립트가 트랜스크립트 없는 항목은 역할 파일로 새로 시작).
- **멈춘 세션은 그동안 온 회신을 못 받는다.** 재시작할 때 지시에 "멈춰 있는 동안 끝난 일"(커밋 해시, 병합, 결정)을 넣는다. `{{docs.progress}}`의 "역할별 다음 할 일"을 지시·완료 때마다 갱신한다.
- **메모리는 세션을 시작한 뒤 잰다.** 세션이 시작될 때 순간 수백 MB를 쓴다. 무거운 작업 지시는 시작한 상태에서 {{memory.blockFreeMB|size}} 이상이면 진행. 동시 세션 수는 고정하지 않고 메모리를 보며 늘린다.
- 세션 교체: `health`의 권장이 '세션 교체'(컨텍스트가 교체 기준 이상, 기본 10만 토큰, 토큰을 못 읽으면 {{rotation.transcriptMB}}MB 이상)이거나 큰 작업·단계가 끝났으면 `prep` → 회신(경로 또는 진행 중 없음) → `rotate` → 새 세션 시작 회신 → 끝난 일 전달. 작업 경계에 맞추면 인수인계 없이(`none`) 세션을 교체한다.
- {{pmRole}} 세션 교체(백그라운드 {{pmRole}}): 보통은 사용자가 세션 현황 pm 줄의 [pm 교체]를 누르면 붙기 터미널로 "pm 세션 교체 — 진행 중인 것을 저장하고 start-pm -Force로 새 pm을 띄운 뒤 이전 pm을 멈춰 줘"가 들어온다. 받으면 하던 턴을 마친 뒤: 자기 진행 중인 것만 `/wy-save-session`(short-id {{pmRole}}) → `start-pm <경로> -Force`(새 {{pmRole}}을 띄우고 이전 세션 id를 알려 줌) → 사용자에게 "`session.ps1 attach {{pmRole}}`로 새 pm에 붙으세요" 한 줄(세션 현황이 지켜보다 새 터미널로 붙여 준다) → 마지막 동작으로 이전 자신을 `claude stop <이전 id>`. 그 사이 같은 이름이 둘이라 `ListAgents`의 ref로 구분한다. `pm-cmd`가 이 순서를 출력한다.
- **새 {{pmRole}}이 시작한 직후 `ListAgents`에 자기 말고 같은 {{pmRole}} 이름이 보이면 교체 직후 남은 항목이다.** 멈춘 이전 pm이 몇 분 동안 'busy'로 남는다(`claude agents --json --all`에서는 stopped, pid 없음). 중복 {{pmRole}} 여부는 `session.ps1 list`의 실행 중(pid 있음) 항목으로만 판단한다(실행 중인 같은 이름이 둘이면 list가 '중복 실행'을 출력). 실행 중 {{pmRole}}이 하나면 경고하지 않고, {{pmRole}} 이름으로 `SendMessage`를 보내지 않는다.
- 백그라운드 세션의 권한 요청 창은 사용자가 승인할 수 없다. 지시에 "권한 요청이 필요한 동작은 하지 말고 [차단]"을 넣고(역할 파일에도 있음), 대시보드의 승인 대기(노랑 삼각형)는 진짜 승인 대기다. 입력 대기(초록 점)는 일을 마치고 쉬는 상태.
- `claude attach`로 깨운 백그라운드 세션은 `--agent` 없이 재시작될 수 있다. 그러면 가드 훅이 그 세션을 {{commitRole}}로 보지 않아 커밋이 막힌다. 사용자가 권한 요청 때문에 attach했으면 그 뒤 {{commitRole}}은 `rotate {{commitRole}} none`으로 세션을 교체한다. attach는 `!`로는 안 되고 별도 터미널에서 해야 한다.
- 권한 요청 대기는 사용자가 알아채지 못한다. 그런데 `claude agents`의 `state: blocked`는 일을 마치고 쉬는 백그라운드 세션에도 나와 그대로 알리면 거짓 알림이 된다. 그래서 상시 감시(Monitor)는 걸지 않는다. 세션이 오래 답이 없거나 blocked로 보이면 `claude logs <id>`의 마지막 줄로 권한 창인지 먼저 확인하고, 권한 창일 때만 사용자에게 알린다.
- `decisions.log`의 `kind:"stuck"` 줄은 결정이 아니라 멈춤 의심 알림이다(세션이 도구 한 번에 기준 분 이상 묶여 메시지를 못 받음). 세션을 재시작하지 말고 먼저 살핀다(`claude logs <id>`). 그다음 `notice`대로: 막힌 원인을 풀거나, 사용자에게 `claude attach`를 권하거나, 필요하면 멈추고 다시 띄운다.

## 6-2. 백그라운드 {{pmRole}}에 붙기

- {{pmRole}}은 호스트의 백그라운드 세션 하나로만 돈다. 사용자가 세션 현황 pm 줄 [pm 시작](또는 설치 마법사 마침, `session.ps1 start-pm latest`)으로 띄우고, [붙기](통합 터미널 '{{pmRole}} 붙기', `session.ps1 attach {{pmRole}}`)로 말을 건다. pm 줄은 상태·컨텍스트(토큰)·[pm 교체]·[멈춤]을 보여 준다.
- 붙기 터미널에서 빠져나오거나 접속 PC를 닫아도 {{pmRole}}은 계속 돈다.
- `!`로 실행한 명령은 화면을 주고받지 못한다. `claude attach`처럼 대화형 화면이 필요한 명령은 사용자에게 별도 터미널에서 실행하게 한다.
- VS Code 리로드·재시작 뒤에 {{pmRole}}이 걸어 둔 감시(Monitor: 권한 요청 대기)가 끊겼으면 다시 건다. 결정 수신은 훅이 하므로 다시 걸 것이 없다.
