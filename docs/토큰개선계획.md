# wy-ops 토큰 사용 개선 계획 (TOK)

- 담당: OPS-pm. 시작 2026-10-14(사용자 지시, D-20). S2~S5보다 먼저 한다.
- 근거: erp 토큰 사용 조사(`docs/조사/20261014-erp-토큰사용/`, 미커밋·이 PC에만), Claude Code 공식 문서(비용·프롬프트 캐시·모델 설정).

## 출발점

비용 ≈ Σ(호출마다 다시 읽는 문맥). erp 2026-10-09~13: 약 41억 토큰 중 캐시 읽기 96.8%, 호출 28,254번, 호출당 평균 문맥 14.3만. 줄일 수 있는 것은 셋이다.

1. 문맥 크기 — 호출 1번이 다시 읽는 양
2. 호출 수 — 도구 호출, 메시지 왕복, 대기 루프, 쉬는 세션 깨우기
3. 기본 문맥 — 모든 호출 앞에 붙는 시스템 프롬프트·스킬 목록·MCP 도구

## 공식 문서에서 확인한 사실(2026-10-14)

- 1M 문맥 모델(Opus 5.5 등)은 기본으로 약 967K에서야 자동 압축한다. `autoCompactWindow`(100K~1M)로 낮출 수 있다.
- 쉬는 세션에 온 세션 간 메시지는 새 턴으로 전달되어 전체 문맥을 보낸다(`crossSessionInbound: hold`로 보류 가능).
- 메인 대화 캐시 수명은 구독 안에서 1시간, 사용량 크레딧이면 5분. 그보다 오래 쉰 세션을 깨우면 전체를 다시 쓴다.
- `/compact`는 대화 전체를 읽는 큰 요청이다. 새 세션(rotate)·`/clear`는 비용이 없다.
- 모델·effort를 세션 중간에 바꾸면 캐시가 깨진다(역할 파일에서 처음부터 지정).
- PreToolUse 훅으로 테스트 출력을 실패 줄만 남기는 방식이 공식 예시로 있다.

## 단계

| 단계 | 할 일 | 줄이는 것 | 담당 |
|---|---|---|---|
| TOK-0 | 기준선 측정: 역할별·일별 토큰과 호출 수, 호출당 평균·최대 문맥, 세션 길이, 깨우기 턴(메시지·Stop 훅) 수, 도구별 호출 수, 기본 문맥 크기(세션 첫 요청의 캐시 생성량). 두 저장소. 같은 방법으로 단계마다 다시 잰다 | (측정) | OPS-review |
| TOK-1 | 문맥 상한: 세션 교체 기준을 알림이 아니라 실제로 지키게 함, `autoCompactWindow` 안전망 | 문맥 크기 | OPS-dev2, 설정은 사용자 카드 |
| TOK-2 | 깨우기 줄이기: commit 승인 대기 루프 → 결정 깨우기 훅, 메시지 묶어 보내기, Stop 훅 알림이 필요한 때만 턴을 만들게, 오래 쉴 세션은 깨우지 말고 멈춤 | 호출 수 | OPS-dev1(훅)·OPS-dev2(템플릿)·pm 규칙 |
| TOK-3 | 호출 줄이기: 'ListAgents 매번' 규칙 완화, 파일 한 번에 읽기, 시험 출력 거르기 훅 | 호출 수·결과 크기 | OPS-dev2·OPS-dev1 |
| TOK-4 | 기본 문맥 줄이기: 역할 세션에서 안 쓰는 플러그인·MCP 끄기(`ecc:context-budget`으로 감사, `ecc:config-gc`로 정리) | 모든 호출의 공통 부분 | 사용자 설정 카드 |
| TOK-5 | 모델·effort: 기계적인 역할은 Sonnet·낮은 effort를 역할 파일 frontmatter로 | 단가 | 역할 원본(.claude/ops), pm |

순서: TOK-0 → (TOK-1·TOK-2·TOK-3 병행, 담당 영역별) → TOK-4 → TOK-5. 단계마다 TOK-0과 같은 방법으로 다시 재서 효과를 확인한다. 효과 수치는 측정 전까지 추정이다.

## TOK-0 기준선(2026-10-14, OPS-review)

자료: `docs/조사/20261014-TOK0-기준선/`(summary.md·스크립트·원자료, 미커밋). 호출 중복은 (message.id, requestId) 전역 기준으로 제거했다. 그래서 이전 조사의 41억·28,254호출은 실제로 38.4억·26,023호출이다. 총량은 agent-cost-report와 맞음.

| | erp(10-09~13) | ops(10-13~14) |
|---|---|---|
| 토큰(메인) / 호출 / 세션 | 3,790.6M / 25,497 / 410 | 136.5M / 926 / 13 |
| 호출당 평균 문맥 | 148k | 147k |
| 단가 가중 비중(읽기·생성·출력) | 66·21·12% | 63·23·14% |
| 메시지·알림으로 시작한 턴 비중(수/토큰) | 79% / 83% | 70% / 79% |
| 기본 문맥(세션 첫 호출 중앙) | 64k | 55k |

상위 원인:
1. 긴 세션: 호출당 평균 148k, 상위 세션 270k·압축 2~4번. 교체 기준이 안 지켜짐 → TOK-1
2. 메시지 왕복: SendMessage+ListAgents 4,597번(호출 18%, 약 6.8억 추정 상한). 받고 답만 한 짧은 턴 837개(1.6억) → TOK-2·3
3. Bash 조각 읽기: grep·sed -n·cat 7,198번, 도구 결과가 큼 → TOK-3
4. agent-browser CLI 3,997번, 스냅숏이 문맥에 쌓임 → TOK-3
5. commit 대기 구조: 깨우기 턴 96%, 대기 루프 499번. 1시간 넘게 쉰 뒤 깨워 캐시를 다시 쓴 경우 30건(최대 25만) → TOK-2

기본 문맥 구성(글자 수 추정): 스킬 목록 40.7k자, 에이전트 목록 26.7k자, CLAUDE.md·메모리 7~17k자, 훅 출력 약 12k자 → TOK-4.

## pm 결정(2026-10-14, TOK-0 근거)

- 세션 교체 기준: `rotation.contextTokens` 150k → 100k, `notifyTokens` 200k → 130k. 근거: 새 세션 비용(기본 문맥 약 64k 캐시 생성)은 평균 문맥이 58k 줄면 호출 약 22번 안에 회수되고, 세션당 평균 호출은 136~211번이다.
- 안전망: 프로젝트 settings에 `autoCompactWindow` 200000.
- 쉬는 세션 정책(D-21, 사용자 결정): 1시간 넘게 안 쓸 세션은 stop, 다음 작업은 교체 기준 이상이면 rotate.
